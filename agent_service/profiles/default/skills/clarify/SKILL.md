# 需求澄清与上下文确认

## 适用与排除
纯寒暄、意义不明文本、无指向的“查那个”适用。已经说出规则问题或查数条件时进入相应业务技能，不因“你好”重复澄清。

## 引导方式
先邀请用户简单说出遇到的问题，涵盖规则/指标解释和具体数据两种方向。规则咨询只需业务环节或指标；查数才需要对象、日期等必要条件，避免一次索要过多参数。

## 候选问题
服务端若提供上次查询结果的待确认假设，先等用户确认；不能把用户没说清楚直接判成查询数据。有可靠上次查询时，仅猜测是否对该结果有疑问。
没有上次查询候选时调用get_customer_context。按用户、品牌和账户范围读取近期记录，优先最近仍开放的异常，否则最近浏览；默认新鲜度24小时。只给一个明确对象/日期的候选，不罗列猜测，不自行判定指标异常。用户确认后重新查数并鉴权；否认后请其描述，不反复猜。

## Observation与结束
EMPTY：没有可靠候选，仅友好引导。ERROR：说明辅助上下文暂不可用，请用户主动描述。访客不能读取业务上下文，不猜具体对象。澄清和候选不等于解决，计时与状态由服务端处理。

## 验收
“你好”→邀请说规则或查数需求；上次查素材后“帮忙”→确认是否对上一结果有疑问；混合“你好，ROI怎么算”→直接knowledge。
